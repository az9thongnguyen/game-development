# 141 — Four runs of one script

Chapter 140 ended with a script that failed on purpose:

```
$ sh baas/ops/pg-test.sh
ERROR:  syntax error at or near ","
LINE 1: INSERT INTO schema_migrations(version, name) VALUES(?,?)
```

That was the first statement this repository had ever sent to a real PostgreSQL,
and it was the first line of the schema. `db.h` had described Postgres as "a
documented deploy-time build" since the backend's first slice. It was a sentence.

This chapter is the four runs of that script it took to make it a capability, and
what each one found. The interesting part is not the fixes — most are three lines.
It is that **all four failures were invisible on SQLite, and all four were in code
that had tests**. The suite was green through every one of them.

---

## Run one: `?` is not a placeholder

Drogon does not translate `?` into `$1`. Every one of the 107 queries in `baas/`
is written with `?`, so the answer had to be one translation, in one place, that
nothing could go around.

`web::db::portable(sql, dialect)` is that place. It is pure and total — a string
in, a string out — so `test_baas_sql_seam` reads its **values** with no database
anywhere near it. Four rewrites, and each one is a disagreement no call site could
have fixed for itself:

| written here | SQLite | Postgres |
|---|---|---|
| `?` | `?` | `$1`, `$2`, … |
| `AUTOID` | `INTEGER PRIMARY KEY` | `INTEGER PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY` |
| `CURRENT_TIMESTAMP` | `CURRENT_TIMESTAMP` | `to_char(now() at time zone 'utc','YYYY-MM-DD HH24:MI:SS')` |
| `BYTELEN(x)` | `length(CAST(x AS BLOB))` | `octet_length(x)` |

`AUTOID` is a **token** rather than a pattern match on `INTEGER PRIMARY KEY`,
because `schema_migrations.version` is an `INTEGER PRIMARY KEY` that is *not* a
surrogate — the version number is supplied — and a rewriter clever enough to guess
would have been wrong about exactly that one.

`CURRENT_TIMESTAMP` is there because every timestamp column in this schema is
`TEXT`, and Postgres will not put a `timestamptz` in one: not as a `DEFAULT`, not
in an `UPDATE`, and not on either side of a comparison. `to_char` rather than
`now()::text`, because Postgres's own text form carries microseconds and a zone
offset, and `live_events` compares those strings to each other with `<=`.

Quoted text is copied through untouched, doubled quote and all. A `?` inside a
string literal is data.

Then the seam. `db::exec(conn, sql, …)` is the one door — a template, so a caller
never has to know whether it is holding a `DbClientPtr` or a transaction — and
`db::insert_id` is the one place a new row's id comes from, because SQLite answers
that from the connection afterwards and Postgres needs `RETURNING` **in** the
statement. 104 call sites moved onto them and eight `insertId()` onto `insert_id`.

And then the part that makes it a seam rather than a convention: the second half
of `test_baas_sql_seam` reads the source tree and fails if `execSqlSync` appears
anywhere else. A line may opt out with a trailing `// raw-sql: <why>` — a file may
not. There are nine in the tree, they are printed, and they are counted, so
growing that number is a visible act. Five are in `db.h`, where the seam is built;
two are in a test helper that runs DDL before any dialect has been chosen; two are
in the search itself, where the pattern is the needle.

The scan earns its keep immediately. Half the tests **insert the project they then
talk to**, and a fixture written in `?` fails on Postgres exactly as loudly as a
service does — one slice later, in a test whose name says "leaderboard".

## Run two: a parameter has a width

The schema now built. Then, fifty-eight times:

```
ERROR:  incorrect binary data format in bind parameter 1
CONTEXT:  unnamed portal parameter $1
```

Drogon binds an integral parameter in **binary** — `sizeof(T)` raw bytes, network
order, with no type OID:

```cpp
case 8: *std::static_pointer_cast<uint64_t>(obj) = htonll((uint64_t)parameter); break;
…
lengths_.push_back(sizeof(T));
formats_.push_back(1);
```

Postgres infers the parameter's type from the column and then insists the payload
be exactly that wide. Every id column in this schema is `INTEGER` (four bytes) and
every id in this code is a C++ `long` (eight).

The tempting fix is to make the widths agree. That is a rule with no test, held
across a hundred call sites, failing at runtime on the one backend nobody develops
on — the exact shape of the problem this slice exists to end. **A text parameter
has no width.** Postgres coerces an untyped literal to whatever the column is, so
`int`, `long` and `long long` all arrive as the same thing and none of them can be
the wrong size. SQLite is left alone, where the binding is typed and correct.

Two more things fell out of the same run:

`length(CAST(data AS BLOB))` is SQLite for "how many bytes" — `length()` there
counts characters. Postgres has no `BLOB` type at all. Hence `BYTELEN`, the one
rewrite that has to read its own argument.

And six tests opened with this line:

```cpp
const long pid = 1;   // a project id; no FK enforcement needed for this unit test
```

That comment was not a design decision. It was a description of SQLite's default:
`PRAGMA foreign_keys` is **off**, so a row pointing at a project nobody created is
accepted without complaint. Postgres enforces the constraint the schema asked for,
and against it those six tests could not insert a single row. A year of green runs
over data no real deployment would have held. `baastest::make_fixture` makes a
project and a player that exist.

## Run three: a lock cannot hold a row that is not there

Now the SQL all ran, and `test_baas_concurrency` did this:

```
  10 bought, 38 refused, 0 errored; gold 0, swords 10
ERROR:  duplicate key value violates unique constraint "inventory_project_id_user_id_item_key"
ERROR:  duplicate key value violates unique constraint "inventory_project_id_user_id_item_key"
ERROR:  duplicate key value violates unique constraint "inventory_project_id_user_id_item_key"
  45 grants of 1 -> 45 shells
```

Chapter 140 put a transaction and a locking read in front of every read-then-write
and believed it was done. `FOR UPDATE` locks a **row**. The first write to a key
has none: both threads read nothing, both take the INSERT branch, and one of them
loses to a unique constraint. Chapter 140 closed the second write and left the
first one open — and the test it wrote to prove the fix could not see it, because
on SQLite the pool of one serialises the pair.

The idiom is: **materialise, then lock.**

```cpp
template <typename Conn, typename... Args>
bool ensure_row(const Conn& conn, const std::string& insert_sql, Args&&... args) {
    return exec(conn, insert_sql + " ON CONFLICT DO NOTHING",
                std::forward<Args>(args)...).affectedRows() > 0;
}
```

`ON CONFLICT DO NOTHING` with the target omitted means "any conflict" in both
SQLite (3.24+) and Postgres (9.5+). The loser of the race blocks until the winner
commits and then does nothing, which is exactly right: the locking read that
follows finds the winner's row. And it returns whether *this* call created the row,
which is the same answer `existing.empty()` used to give and is now atomic — that
is what `lb::submit` needs to know whether a submission is a new entry.

Two branches disappeared along the way. `put_qty` no longer takes an `exists` flag
and `store_rating` no longer has an INSERT arm: every caller materialises first, so
there is one way to write a quantity and one way to store a rating.

Then the search for the same shape elsewhere, which found four more — `cfg::set`,
`store::upsert`, `save::put`, `asset::put` — all read-then-write, **none of them in
a transaction at all**. There the loser of the race is not a failed request; it is
an uncaught exception on a Drogon event-loop thread, which is to say the server
process, from `POST /v1/saves/{slot}`. The first two never need the old value and
became single `ON CONFLICT … DO UPDATE` statements. The other two bump a version,
so they materialise and lock like the rest.

`test_baas_concurrency` grew a fourth section for them: one key, one sku, one slot,
one asset, each written for the **first** time by eight threads at once. Every call
must succeed, none may throw, and the version afterwards must count every write.

## Run four: the pool of one was also a memory barrier

No SQL errors left. Every number wrong.

```
FAIL  web::inv::get(pid, uid, "gold").qty == kFunds
  48 grants of 1 -> 47 shells
FAIL  web::inv::get(pid, uid, "gold").qty == 70
```

Not a lost update — a write that had not landed. Most of those failures are
single-threaded: grant, then read, then compare.

Drogon commits a transaction in its destructor, and the `COMMIT` is **enqueued** on
that connection's event loop rather than executed there and then. With a pool of
one, whatever the caller does next queues behind the commit on the same connection,
so it always sees it. With a real pool, the next statement takes a *different*
connection and reads the state from before the commit. `grant` returned 8 and the
`GET` immediately after it returned 7.

That is the third thing the pool of one had been silently providing — after
atomicity (chapter 140) and a row for the lock to hold (run three): read-your-own-
writes. An HTTP API cannot give that up. A `POST` that answers before its commit is
real leaves the `GET` after it entitled to be older.

```cpp
Transaction::~Transaction() {
    const bool wait = !rolled_back_;
    tx_.reset();   // this is what enqueues the COMMIT
    if (!wait || !done_.valid()) return;
    if (done_.wait_for(std::chrono::seconds(10)) != std::future_status::ready)
        std::fprintf(stderr, "db::Transaction: commit did not report within 10s\n");
}
```

Bounded, because chapter 140 already spent twenty-five minutes inside a wait that
could not finish and reported nothing; a timeout here is a message, not a hang.
And `rollback()` deliberately does **not** wait: the caller is on an error path,
is returning a failure, and has nothing to read back — which also means this class
never depends on whether Drogon fires the commit callback for a rollback.

`30/30` on Postgres. `89/89` on SQLite.

## What the mutations found

Twenty-seven single-token mutations: twenty-one against SQLite, six inside the
container against Postgres.

Two survived the first pass, and both were real.

**A whole-word test written in the wrong case.** `portable` matches `AUTOID` and
`CURRENT_TIMESTAMP` case-sensitively, and the test that was supposed to prove it
only rewrites whole words said:

```cpp
EQ(portable("SELECT autoidx, my_autoid FROM t", pg), "SELECT autoidx, my_autoid FROM t");
```

Lowercase. The matcher never looked at those strings twice, so deleting the
trailing-boundary check from `word_at` changed nothing the test could see. The
assertion had been passing for a property it was not exercising. Now it is
`AUTOIDX` and `MY_AUTOID`, and the mutation dies — as does its mirror image, the
leading-boundary check, which nothing had ever tested at all.

**A refused write that kept the row it materialised.** `save::put` and `asset::put`
create the row *before* checking `If-Match`, so a 409 that forgot to roll back
publishes an empty save under a slot that never existed. Both roll back; neither
had a test that would have noticed. Both do now: an `If-Match` against a name that
does not exist must 409 **and** must leave a 404 behind it.

The rest died, including every one of the six Postgres-only ones — the identity
column, the timestamp type, the binary parameter, the row lock, the `RETURNING`,
and the waited-for commit.

## What this cost, and what it bought

`?`→`$n` was the headline in chapter 140 and it was the smallest of the four. The
other three were not syntax; they were three different things one connection had
been doing on the code's behalf, none of them written down, all of them load-bearing.

The general shape is worth naming: **a single-connection backend is not a small
version of a pooled one.** It is a different set of guarantees, and every one it
gives away for free is a guarantee some code has come to depend on without saying
so. Atomicity, a row to lock, and a visible commit — three, and the only way to
find out was to run the tests somewhere else.

Which is now what happens. `baas-test` in CI grows a `postgres:16-alpine` service
and runs the same suite **twice**, once against each backend. Not a different suite
and not a subset: `BAAS_TEST_DB` points every test at Postgres and each one wipes
the schema on the way in. A query that parses in SQLite and not in Postgres fails
in the test that already covers the feature, and nobody has to remember to write it
twice.

`baas/ops/pg-test.sh` stays, with a new header. It was a reproduction; it is now
the way to bisect a Postgres-only failure without pushing.

The ledger line that said **❌ Postgres does not work** says `✅` and gives a date.
